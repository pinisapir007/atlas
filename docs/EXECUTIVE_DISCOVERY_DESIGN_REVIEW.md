# Executive Discovery — Design Review (Milestone 1, ATLAS v2)

**תאריך:** 2026-08-11
**מטרה:** תכנון הנדסי מדויק, לא פילוסופי, לשלושת המנגנונים שננעלו. זהו המסמך האחרון לפני שורת הקוד הראשונה.

**מבחן מנחה לכל סעיף במסמך הזה** (כפי שהוגדר): האם זה מקרב את ATLAS להיות המנכ"ל הדיגיטלי שאנחנו בונים? כל תוספת שלא עוברת את המבחן הזה סומנה ככזו במפורש, לא נכללה בשקט.

---

## עיקרון מארגן: איפה שלושת המנגנונים יושבים

שלושתם **אינם שכבה חדשה ואינם רכיב חדש** — הם הרחבה של **Executive Decision** עצמה. `decide()` כבר עושה בדיקת סף קבועה אחת (`MIN_INDEPENDENT_SOURCES`) לפני שהיא מרשה verdict. שני מנגנונים חדשים (Exploration Gate, Threshold) הם בדיוק אותו סוג בדיקה — נוספים לפני/לצד הבדיקה הקיימת, לא מנגנון נפרד. מנגנון שלישי (Research Trigger) חוצה את הגבול בין Business Brain ל-Agentic OS באופן טבעי — בדיוק כמו כל שאר הגשרים הקיימים במערכת (`hands/dispatch.py` הוא התבנית המדויקת: החלטה שכבר התקבלה הופכת ל-Task אמיתי, מנותב דרך Delegator הקיים).

---

## מנגנון 1 — Exploration Before Commitment

| | |
|---|---|
| **מטרה** | למנוע מ-Decision להגיע ל-verdict מחייב לפני שנבדק מרחב רחב מספיק של קטגוריות עסקיות — לא רק מה שכבר יש לו Finding. |
| **קלט** | (א) קבוצת ה-Findings הקיימת לקטגוריה/goal הנבדק; (ב) טקסונומיה מפורשת, ניתנת-לעריכה, של מודלי עסקים (**חדש** — קבוע דוגמת `MARKET_LOCALE`/`HASHTAG_PLATFORMS`, לא ישות Domain); (ג) כיסוי ראייתי אמיתי לכל קטגוריה בטקסונומיה. |
| **פלט** | verdict בוליאני "רוחב מספיק / לא מספיק" + אם לא מספיק — רשימת הקטגוריות הספציפיות שטרם נבדקו (עובר ישירות למנגנון 2). |
| **ישויות Domain** | קורא `Finding` (קיים). לא כותב שום דבר — בדיקה מחושבת-מחדש בכל קריאה (Projection, כמו `confidence_score()`). |
| **שכבה** | בתוך **Executive Decision** — בדיקת סף נוספת, מאותו סוג בדיוק כמו `MIN_INDEPENDENT_SOURCES` הקיים. |
| **מי מפעיל** | Decision, אוטומטית, בכל קריאה ל-`decide()`. |
| **מי צורך את הפלט** | אם עבר → Decision ממשיכה כרגיל. אם לא עבר → verdict חדש (`exploration_incomplete`) → מנגנון 2. |
| **ממחזרים** | `Finding.category`, דפוס "קבוע ניתן-לעריכה" (`MARKET_LOCALE`). |
| **חדש לגמרי** | הטקסונומיה עצמה; פונקציית הבדיקה; ה-verdict `exploration_incomplete`; מספר-הסף (N קטגוריות מינימום) — צריך להיות קבוע מפורש, גלוי, ניתן לעריכה, לא נגזר במרומז. |

## מנגנון 2 — Research Trigger

| | |
|---|---|
| **מטרה** | כש-Decision מחזירה `insufficient_evidence` או `exploration_incomplete` — ליזום בפועל מחקר ממוקד, במקום להמתין בפסיביות ל-Finding שיגיע. |
| **קלט** | ה-verdict + תיאור הפער הספציפי (איזו קטגוריה/subject חסר ראיות עליה). |
| **פלט** | `Finding`(ים) אמיתיים, ממוקורים, עם timestamp — נכתבים ל-KnowledgeBase, באותה צורה בדיוק כמו כל מנגנון איסוף Finding קיים היום. |
| **ישויות Domain** | קורא את תיאור הפער; כותב `Finding` (קיים לגמרי — משתמש גם בשדות `subject`/`market` שכבר נוספו בעבודת Opportunity Discovery V1). |
| **שכבה** | **חוצה את הגבול, בכוונה ובבירור**: מה לחקור נקבע ב-Business Brain (Decision — תלוי-מדיניות); איך מבצעים את החיפוש בפועל הוא Agentic OS טהור (דלגציה מכנית, ללא שיפוט) — בדיוק אותה חלוקה שכבר קיימת ב-`hands/dispatch.py`. |
| **מי מפעיל** | Decision's verdict → יוצר Task אמיתי (קטגוריה חדשה, למשל `request_research`) — אותו דפוס בדיוק כמו `decision_apply.py` היום עבור `propose_capability`, רק לא risk-gated (זו פעולה הפיכה, זולה, ללא סיכון אמיתי). |
| **מי צורך את הפלט** | ה-Finding החדש זמין ל-Perception/Decision במחזור **הבא** — לא הזנה ישירה, בדיוק לפי עקרון Continuous Operation (Domain הוא מנגנון התיאום היחיד). |
| **ממחזרים** | `Task`/`Delegator`/`Registry.dispatch()` (ללא שינוי), `Finding`, `KnowledgeBase.save_finding()`. |
| **חדש לגמרי** | קטגוריית ה-Task; הענף החדש ב-`decision_apply` שיוצר אותה. |

### ⚠️ ממצא קריטי — רכיב רביעי חסר, לא "מנגנון" אלא Agent אמיתי

בדקתי את זה בפועל (לא בהנחה) בסבב הקודם: **אין היום שום Agent רשום שיכול לבצע "תן לי נושא, תביא לי מקורות אמיתיים."** `GeminiProvider` פועל רק על תוכן שכבר סופק. `MarketSignalProvider`/`OpportunityProvider` הם Protocols ריקים. משמעות הדבר: אם Milestone 1 ייבנה כשלושת המנגנונים בלבד, **מנגנון 2 ייצור Tasks שאין למי להאציל אותם** — בדיוק אותה תבנית כשל מדויקת שזיהינו אתמול (MAYA כ-stub, אף Agent לא יכול לבנות ממשק). לפי המבחן שקבעת ("האם זה מקרב את ATLAS להיות המנכ"ל?") — מנגנון שיוצר משימות שאף אחד לא יכול לבצע **לא עובר את המבחן**, גם אם הלוגיקה שלו נכונה לחלוטין.

**המסקנה שלי: Milestone 1 חייב לכלול גם Agent מינימלי, אמיתי, שמסוגל לבצע מחקר-נושא-פתוח** — לא מנגנון רביעי בהיגיון של Decision, אלא Asset אמיתי בצד ה-Agentic OS, כדי ש-Executive Discovery תהיה בת-בדיקה מקצה-לקצה ולא תיאוריה. יש נתיב בנייה ריאלי בלי אינטגרציית credentials חדשה: `browser_use_observer.py` כבר עובד ואומת — אפשר לכוון אותו למנוע חיפוש אמיתי ולחלץ תוצאות דרך אותו דפוס בדיוק שכבר קיים (הצביר של audio/document/image/video/youtube plugins שכבר סומן כקוד הכי נקי בבסיס). זה לא Scope Creep — זו התנאי המוקדם שהופך את מנגנון 2 לאמיתי.

## מנגנון 3 — Research Completion Threshold

| | |
|---|---|
| **מטרה** | סף עצירה מפורש וקבוע, שמונע לולאת מחקר אינסופית (Exploration→insufficient→Research→re-Exploration→...). |
| **קלט** | מצב הראיות הנוכחי לקטגוריה (משתמש בפונקציות הקיימות ב-`confidence.py`) + מונה ניסיונות-מחקר לאותה קטגוריה/subject. |
| **פלט** | בוליאני "עצור, המשך ל-Decision עם מה שיש" / "המשך לחקור" — **ואם לאחר N ניסיונות עדיין אין מספיק ראיות: verdict כן חדש (`insufficient_evidence_after_research`), לא שקט אינסופי.** |
| **ישויות Domain** | קורא את אותם factors כמו `confidence_score()`. כותב מונה ניסיונות — **לא ישות חדשה**, ממחזר את דפוס ה-metric הגנרי הקיים של `KPIRegistry` (`research_attempts_{category}`). |
| **שכבה** | אותה שכבה כמו מנגנון 1 — בדיקת סף בתוך Executive Decision. |
| **מי מפעיל** | Decision, בכל קריאה. |
| **מי צורך** | Decision עצמה — אם "עצור", ממשיכה עם הראיות שיש (או מחזירה verdict כן חדש אם עדיין לא מספיק). |
| **ממחזרים** | פונקציות evidence-factor קיימות ב-`confidence.py`, דפוס `KPIRegistry`. |
| **חדש לגמרי** | מונה הניסיונות; קבוע ה-max-attempts (מפורש, ניתן-לעריכה, כמו `MIN_INDEPENDENT_SOURCES`); ה-verdict `insufficient_evidence_after_research`. |

**הערה חשובה:** ה-verdict החדש הזה (`insufficient_evidence_after_research`) הוא בדיוק המקום הראשון שבו נחוצה תקשורת יוצאת יזומה למייסד (הפער שזיהינו אתמול — "explicitly deferred"). **אני לא ממליץ לבנות את ערוץ ההתראה בפועל בתוך Milestone 1** — זה scope נפרד, גדול יותר. אבל חשוב לוודא שה-verdict עצמו נכתב בצורה שמאפשרת בעתיד לחבר אליו תקשורת יוצאת, בלי לשנות את Decision שוב.

## סיכום: מה נבנה, מה ממוחזר, מה עדיין פתוח

**נבנה בפועל ב-Milestone 1:**
1. טקסונומיית מודלים עסקיים מפורשת (קבוע דאטה קטן).
2. שתי בדיקות סף חדשות בתוך `decide()` (רוחב, עצירת-מחקר) + שני verdicts חדשים (`exploration_incomplete`, `insufficient_evidence_after_research`).
3. ענף חדש ב-`decision_apply` שיוצר Task מסוג `request_research`.
4. **Agent מינימלי אמיתי** למחקר-נושא-פתוח, מבוסס על `browser_use_observer.py` הקיים — ללא credentials חדשים.
5. מונה ניסיונות-מחקר (משתמש ב-`KPIRegistry` הקיים).

**ממוחזר ללא שינוי:** `Finding`, `Task`/`Delegator`/`Registry.dispatch()`, `confidence.py`'s factor functions, `KnowledgeBase`, `KPIRegistry`.

**נשאר פתוח בכוונה, לא נבנה כאן:** ערוץ תקשורת יוצאת למייסד (verdict החדש רק "מוכן" לזה); ההכרעה הארכיטקטונית של Milestone 0 (רוויזיה/ריפקטור/מקבילי) — תיפתר באופן טבעי ואמפירי דרך העבודה על היכולת הזו עצמה, כפי שהוסכם.

**שני מספרים שצריך לקבוע בפועל בזמן הבנייה, לא כאן:** N (מינימום קטגוריות לרוחב), max-attempts (מחקר). שניהם חייבים להיות קבועים מפורשים, גלויים, ניתנים לעריכה — לא נגזרים מרומז ולא "יפים באוויר".

## תשובה ישירה לשלוש השאלות שלך

- **מורכבות מיותרת?** לא זיהיתי כזו בשלושת המנגנונים עצמם — כל אחד ממנו הרחבה קטנה וממוקדת של `decide()`/`decision_apply` הקיימים, לא רכיב/שכבה חדשים.
- **מנגנון הכרחי חסר?** כן — **לא מנגנון רביעי בהיגיון של Decision, אלא Agent מינימלי אמיתי** למחקר-נושא-פתוח, בלעדיו מנגנון 2 יוצר משימות-יתום. זה חייב להיכלל ב-Milestone 1, לא רק להיות תוצאה שלו.
- **מנגנון לא מוגדר מספיק?** לא — שלושתם מוגדרים מספיק כדי להתחיל, בתנאי שהרכיב הרביעי (ה-Agent) נכלל בהיקף.

עם התוספת הזו — אני מוכן לנעילה ולמעבר לבנייה.
