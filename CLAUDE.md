# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

ATLAS is the CEO of the company: it plans, prioritizes, delegates work to MAYA and future digital assets, monitors execution and KPIs, allocates resources, produces executive reports, and continuously improves the business itself — autonomously by default, with a human approving only irreversible or high-risk actions (large financial commitments, legal agreements, privileged-access changes, destructive operations, and any redesign of the business's own workflows/agents/processes).

Two permanent layers:
- **`atlas.core`** — the asset registry. Adding a new asset — of any kind — never requires modifying core code, and "asset" doesn't presuppose a specific lifecycle (a business or tool may have no running process at all; an agent or workflow might).
- **`atlas.brain`** — the CEO decision-making layer that plans, risk-gates, delegates, monitors, and reports, driving `atlas.core` from above. `atlas.core` never depends on `atlas.brain`.

MAYA is Asset #1. New assets are not created automatically by the brain — where it identifies a capability gap (e.g. no marketing asset exists yet), it produces a `Proposal` for a human to act on, never a file it writes itself.

Three companion documents, each owning a different layer (see each file's own maintenance note): `CLAUDE.md` (this file) owns *how the code is structured*; `docs/ATLAS_BUSINESS_BLUEPRINT.md` owns *what the business does and why*; `HANDOFF.md` owns *current state of the build*, for session-to-session continuation. All three can go stale — cross-check against the code (`python -m pytest -q`, actual file contents) before trusting a specific claim, especially after a gap between sessions.

## Commands

- Install for development: `python -m pip install -e .`
- Running `atlas` with **no arguments** launches the full-screen operator app (`run_app()` in `src/atlas/app.py`) — this is the default entry point, not a CLI-only tool.
- Asset commands: `atlas list` / `atlas info <id>` / `atlas <verb> <id>` where `<verb>` is one of `start|stop|status|run|report`
- `atlas console` — one-shot consolidated operator view (goals, approvals, every department's `report()`, KPIs); same rendering the REPL's `status` command and the full-screen app's dashboard reuse.
- Brain commands: `atlas brain goal add "<description>" --priority N [--horizon short|long] [--expected-revenue N] [--required-investment N] [--time-to-first-profit N] [--scalability 0-1] [--automation-potential 0-1] [--strategic-value 0-1]`, `atlas brain goal list`, `atlas brain task add <goal_id> "<description>" [--category ...] [--amount N] [--reversible] [--privileged-access] [--legal-agreement]`, `atlas brain tick`, `atlas brain status`, `atlas brain approvals`, `atlas brain approve <task_id>` / `reject <task_id>`, `atlas brain proposals`, `atlas brain kpi record <name> <value>` / `kpi list`, `atlas brain report --period daily|weekly|monthly`, `atlas brain finding add <source> <category> "<description>" [--evidence <url>]` / `finding list` — records a real, sourced entry in the Intelligence knowledge base (`atlas/brain/knowledge.py`); `evidence` defaults to `""`, never a fabricated citation, `atlas brain opportunities [--explain]` — ranks every discovered category by evidence-weighted `confidence_score()`; `--explain` shows the full per-category evidence/confidence/expected-ROI/probability-of-success/risk breakdown (`atlas/brain/explain.py`), `atlas brain decisions list` / `decisions show <category>` — full Decision Engine traceability: verdict, confidence, deterministic reasoning, cited evidence Finding IDs, company context, risks, and what a decision superseded if it reopened a prior one (`atlas/brain/decisions.py`)
- Recruitment commands: `atlas recruitment demand add ...` / `supplier add ...` / `candidate add ...`, `atlas recruitment opportunities`, `atlas recruitment approve-outreach <id>` / `approve-commitment <id>` / `lost <id> [--reason ...]`
- Publishing commands: `atlas publishing queue` (list publish packages), `atlas publishing delete <package_id>` (direct housekeeping action, not approval-gated)
- Run all tests: `python -m pytest -q`
- Run a single test: `python -m pytest tests/brain/test_ceo.py::test_tick_delegates_a_new_goal_to_maya -q`
- **No CLI path exists to reactivate a paused `Goal`** — once the Strategist sets `Goal.status = "paused"`, only hand-editing `.atlas/brain.json` can undo it (open gap, see `HANDOFF.md`).

## Architecture: atlas.core (the asset registry)

**Assets are declared by a manifest, not by editing core code.** Each asset is a directory under `src/atlas/assets/<id>/` with a `manifest.toml` (`id`, `name`, `kind`, `description`, `owner`, `tags`, and an *optional* `entrypoint` of the form `module.path:ClassName`). `entrypoint` is optional on purpose — an affiliate business or marketing system may start as pure metadata with no code behind it yet. `kind` is an open string (`agent`, `business`, `marketing_system`, `workflow`, `tool`, `operational_agent`, `revenue_channel`, ...), not a closed enum.

- `src/atlas/core/loader.py` — `discover_manifests()` scans `*/manifest.toml` under the built-in assets dir plus any directories listed in `ATLAS_ASSETS_PATH`. Never imports asset code.
- `src/atlas/core/capabilities.py` — `Runnable` (`start`/`stop`/`status`), `Triggerable` (`run`), `Reportable` (`report`): `@runtime_checkable` `Protocol`s, not a shared base class.
- `src/atlas/core/registry.py` — `Registry` loads `AssetRecord`s eagerly, lazily imports/instantiates an asset's `entrypoint` on first use, and `dispatch(asset_id, verb)` capability-checks and calls it, raising `UnsupportedVerb` if unsupported.
- `src/atlas/core/store.py` — `Store` protocol + `JSONStore` (`.atlas/state.json`) — per-asset last-run state.

## Architecture: atlas.brain (the CEO)

- `src/atlas/brain/models.py` — `Goal` (durable objective; `horizon` — `"short"`/`"long"` — plus an optional `founder_estimate` six-criteria dict and `engine_id` feed the Strategist's capital-allocation scoring, see below), `Task` (one unit of planned work — `category` is an open string like `launch_campaign`/`analyze_revenue`/`redesign_workflow`; carries the four risk axes: `reversible`, `estimated_amount`, `involves_privileged_access`, `involves_legal_agreement`; `source_opportunity_id` is a correlation key set only by a brain-side "pipeline advance" bridge, see below — reused across several bridges to mean "what this dispatch is about", not always literally an opportunity), `Proposal` (a structural decision — create an asset, recruit an agent, or redesign something — that ATLAS cannot execute itself), `Finding` (a durable, channel-agnostic record of something the Intelligence layer discovered — see `knowledge.py`).
- `src/atlas/brain/memory.py` — `BrainMemory`, one JSON document (`.atlas/brain.json`, separate from the asset layer's `.atlas/state.json`) holding goals, tasks, proposals, KPI history, and an append-only decision/outcome log. Storage is delegated to an injectable `BrainStore` (`src/atlas/brain/store.py` — `JSONFileStore` by default, atomic writes, mirroring `atlas.core.store.Store`'s shape) so a future backend can be swapped in without changing `BrainMemory`'s API or any caller.
- `src/atlas/brain/knowledge.py` — `KnowledgeBase`, a separate JSON document (`.atlas/knowledge.json`) holding `Finding`s: a durable record of everything ATLAS's Intelligence layer has discovered, independent of whether a given finding ever became a `Task`/`Goal`. `Finding.category` is an open string (`affiliate`, `digital_product`, `youtube`, `ugc`, ...) — a channel with no dispatchable asset yet is still recorded, never dropped or force-fit into an existing category. `Finding.provider` is optional and orthogonal to category — `""` for a category-general finding, a registered provider name (e.g. `"digistore24"`) when the evidence is about that specific platform, one level deeper than category, which is what `provider_ranking.py` reads to rank platforms within a category. `evidence` defaults to `""`, never a fabricated citation. Reuses the same `BrainStore` abstraction as `BrainMemory`.
- `src/atlas/brain/risk.py` — `RiskPolicy.evaluate(task)`: **fail-closed**. A task must prove itself safe on every axis (reversible, within the amount threshold — default `0.0`, no privileged access, no legal agreement) *and* not be in `ALWAYS_REQUIRES_APPROVAL` (`create_asset`, `recruit_agent`) or start with `redesign_` to skip human approval. Unproven risk defaults to requiring approval, never the reverse. Every founder-approval gate added since (Affiliate Department, Affiliate Intelligence, Content Factory, Editorial Review, Publishing Gateway) reuses this exact mechanism via a plain `reversible=False` `Task` — none of them are a new gating system.
- `src/atlas/brain/planner.py` / `prioritizer.py` — `Planner`/`Prioritizer` protocols with one deterministic default each (`SimplePlanner`, `SimplePrioritizer`). Real, permanent infrastructure — not a stand-in for strategic reasoning. A smarter (e.g. LLM-backed) implementation swaps in behind the same protocol; nothing else in the brain changes. `SimplePlanner` marks its own generated tasks `reversible=True` (they're plain delegate/analyze/report work with no financial/access/legal component by construction) — this is what keeps routine work auto-delegating instead of piling up in approvals.
- `src/atlas/brain/delegator.py` — `Delegator.delegate(task, registry)`: routine tasks get matched to a `Triggerable` asset in the `Registry` and dispatched via `registry.dispatch(asset_id, "run", task=task)`, returning the raw dispatch result (`dict | None`) to the caller; if none match, the task is marked `blocked` (surfaced later as an opportunity/gap, not a silent failure). `is_structural(category)` tasks (gated categories from `risk.py`) always produce a `Proposal` instead — never a dispatch.
- `src/atlas/brain/monitor.py` — `Monitor.sync()` reads back each in-flight task's asset via `Reportable.report()` (falling back to "assumed complete" if the asset doesn't implement it), updates task status, appends an outcome-log entry, and refreshes the brain's own operational KPIs (`tasks_completed`, `tasks_blocked`, `pending_approvals`) — the substrate "learning from results" depends on.
- `src/atlas/brain/intake.py` — `absorb_opportunities()`: turns an asset's self-reported opportunities (e.g. Research's discoveries) into `Task`s under the right `Goal`, deduplicating so the same opportunity is never absorbed twice. Also records every opportunity as a `Finding` in the `KnowledgeBase` regardless of whether it becomes a `Task` — the durable side of intake, `Task` creation is the actionable side.
- `src/atlas/brain/kpi_intake.py` — `record_revenue(task, result, kpis)`: shape-dispatched, fail-closed attribution of a just-completed dispatch's revenue/cost to the correct goal. Revenue-channel shape (`"revenue_generated"` key) is attributed via `task.goal_id` and **accumulated** (one-off incremental amount per execution). Recruitment's shape (`"opportunities"` key) is attributed **only** via each opportunity's own stored `goal_id` (never the dispatching task's), counts only `stage == "won"` as realized, and is recorded as a **replacement reading** (full recomputation each time — idempotent, never inflates on repeated dispatch). An unrecognized/malformed shape (Research's, or anything from the newer affiliate/content pipeline below) records nothing rather than guessing. Called from `CEOBrain._risk_gate_and_delegate()` and `CEOBrain.approve()`, right after `delegate()`, before any later same-tick dispatch can overwrite shared asset state. `record_manual_revenue(goal_id, amount, cost, kpis)` and `record_manual_cost(goal_id, amount, kpis)` (2026-08-03) are the founder-reported paths, both accumulate-semantics: the former for a real conversion (with optional per-conversion cost), the latter for real spend not tied to any single conversion (ad spend, subscriptions, setup cost) — added because affiliate content generation is verified zero-cost (deterministic templates, `content_factory/generator.py`, no LLM/paid API call), so the only real costs in the affiliate channel are founder-known spend with no automatic signal to derive them from. Wired via `atlas affiliate revenue record <package_id> <amount> [--cost N]` and `atlas affiliate cost record <package_id> <amount>` (both resolve `package_id` to `goal_id` via `PublishingQueueStore`). This closes the loop `confidence.py`'s `historical_success_score`/`measured_outcomes_score`/`internal_experiments_score` (50% of total weight) depend on — live-verified: recording cost against a goal with a real `affiliate_pipeline` task moves `atlas brain opportunities --explain` from 1/6 to 3/6 evidence factors and produces a real (non-`None`) Expected ROI.
- **Pipeline-advance bridges** — one small brain-side module per multi-stage asset, all following the same shape first established for Recruitment: read the asset's `report()`, and for each goal-tagged item still in an internal (non-founder-gated) stage, ensure exactly one open "keep going" `Task` exists; once a stage needs a founder decision, create exactly one `reversible=False` task (never repeated for the same item). None of these are a generic framework — each is a small, asset-specific function, deliberately not unified into one engine:
  - `src/atlas/brain/pipeline_advance.py` — `advance_recruitment_pipeline()`, the original, for Recruitment's `discovered → qualified → matched` auto-advance (stops at the `proposal_ready`/`active` founder gates, and at `won`/`lost`).
  - `src/atlas/brain/affiliate_pipeline_advance.py` — `advance_affiliate_pipeline()`, for the Affiliate Department's `discovered → selected → content_planned` auto-advance, then one founder-approval task (with four *projected*, never-real `expected_*_<goal_id>`/`risk_score_<goal_id>` KPIs recorded alongside it — never written to the real `revenue_<goal_id>`/`cost_<goal_id>` series).
  - `src/atlas/brain/affiliate_intelligence_advance.py` — `advance_affiliate_intelligence()`, for Affiliate Intelligence's `discovered → researched → ranked` auto-advance, then one founder-*choice* task **per ranked opportunity** (the founder picks which one to pursue via the existing binary approve/reject, not a new multi-choice mechanism).
  - `src/atlas/brain/content_factory_advance.py` — `advance_content_factory()`: triggers first generation once an opportunity is `selected_for_marketing`, requests founder review once a package is `editorial_passed`, and turns a rejected review into "request changes" (regenerate once, then permanently abandon on a second rejection) — Approve/Reject/Request-changes expressed entirely through the existing binary `approve()`/`reject()` primitive, counted over time.
  - `src/atlas/brain/editorial_review_advance.py` — `advance_editorial_review()`: triggers evaluation once a package is unjudged, dispatches a fix request to Content Factory when revision is required (cross-asset, via the same category-tagged `Task` mechanism every dispatch already uses), and notifies the founder (informational, `reversible=False`) when a package is abandoned after exhausting revision cycles.
  - `src/atlas/brain/publishing_gateway_advance.py` — `advance_publishing_gateway()`: triggers package-building once content is `approved_for_marketing`, requests founder approval to queue a `READY` package, handles a rejection as cancellation, and records a full per-status queue-count snapshot (`publish_queue_<status>_<goal_id>`) every cycle, including zero counts (a status that drops to zero must be recorded as zero, or the last nonzero reading goes stale forever).
- **Intelligence Layer vs. Decision Engine** — a locked architectural boundary (2026-08-02), not an incidental pattern: the Intelligence Layer only ever discovers, verifies, and measures reality; it never recommends, prioritizes, or decides. The Decision Engine is the only component allowed to turn evidence into a business verdict, and never touches the governance boundary (RiskPolicy, `ALWAYS_REQUIRES_APPROVAL`, what requires founder approval) — it can conclude a new asset would be worth building, but `propose_capability` still only ever produces the same `create_asset` Task that's always required approval; it never creates one itself.
  - `src/atlas/brain/confidence.py` — Intelligence: `confidence_score(category, knowledge, memory, kpis)`, a weighted average of six named, evidence-derived factors (`source_corroboration`, `recency`, `repeatability` — always `None`, no real cross-market data exists — `historical_success`, `internal_experiments`, `measured_outcomes`), `WEIGHTS` a stated methodology not fabricated data. A missing factor is never treated as zero; zero available factors returns `None`. `CATEGORY_TASK_CATEGORIES` maps a `Finding.category` to the real, dispatchable Task categories (grepped from every manifest.toml, not guessed) that actually execute that channel — `youtube`/`ugc` map to `set()`, honestly, since no channel exists for either yet. `goals_touching_category()` is the real Task-category linkage every other module in this layer reuses rather than re-deriving. `weighted_average_of_available()` (the fail-closed combination step) and `rank_by_confidence()` (the None-safe, factors_available-tie-broken sort) are shared primitives, extracted (2026-08-02) after both were found independently duplicated in `provider_ranking.py`/`cli.py` — every confidence-based ranking in this codebase goes through these two, not a local reimplementation.
  - `src/atlas/brain/explain.py` — Intelligence: `explain_opportunity()`, the full per-category inspection view — evidence list, confidence breakdown, `expected_roi`/`probability_of_success` (both real or `None`, never guessed), concrete risks, why it ranked where it did. Read-only, on-demand; distinct from `Decision` (below), which is a committed, persisted verdict.
  - `src/atlas/brain/decision_engine.py` — Decision Engine: `decide(category, knowledge, memory, kpis)`, the only function in this codebase allowed to combine Intelligence's context-free `confidence_score()` with company context confidence never sees (existing commitments via `goals_touching_category()`, real execution capability via `CATEGORY_TASK_CATEGORIES`) into one of five verdicts: `insufficient_evidence` (`MIN_INDEPENDENT_SOURCES = 2` — a Decision Engine policy threshold, not an Intelligence fact), `already_invested`, `already_proposed`, `propose_capability`, `invest`. Pure and stateless — no caching, recomputes fresh every call, which is the entire mechanism behind "nothing is permanently true": calling `decide()` again after new evidence arrives *is* reopening the decision. `has_materially_changed()` is the anti-thrash check (`MATERIALITY_THRESHOLD = 0.02`) that stops `recency_score`'s continuous per-tick decay from logging a new Decision every cycle with no real evidence change behind it.
  - `src/atlas/brain/decision_apply.py` — `apply_decision(decision)`: executes exactly one already-made verdict into a real `Goal`/`Task` (or nothing, for the three verdicts that mean no new action). Never decides anything itself — deciding and acting are deliberately two different functions in two different files, mirroring how `Strategist` only returns decisions and `CEOBrain` is the one that applies them.
  - `src/atlas/brain/decisions.py` — `DecisionLog`, a separate JSON document (`.atlas/decisions.json`) holding every `Decision` ever made. Decisions are never mutated or deleted — a changed verdict for a category is a new `Decision` with `superseded_id` pointing at the one it replaced, so the full history of how ATLAS's judgment moved as evidence changed stays on record, inspectable via `atlas brain decisions show <category>`. Reuses `BrainStore`/`JSONFileStore`, same as `BrainMemory`/`KnowledgeBase`.
- `src/atlas/brain/cashflow.py` — pure, side-effect-free: `profit(goal, kpis)`/`roi(goal, kpis)`, computed on read from the existing `revenue_<goal_id>`/`cost_<goal_id>` KPI series — never a stored/fabricated KPI, and `None` (never `0.0`) when either side is unmeasured. `goal_cash_flow(goals, kpis)` is the shared "one entry per goal with revenue-or-cost measured" shape used by both `Reporter.summarize()` and `console.build_console_view()`, so the executive report and the live console can never drift apart on this number.
- `src/atlas/brain/valuation.py` / `scoring.py` — pure, side-effect-free support for the Strategist. `valuation.py` blends a `Goal`'s `founder_estimate` with its measured `revenue_<goal_id>`/`cost_<goal_id>` KPI history per criterion, weighted by `maturity()` (a saturating function of KPI reading count) — the founder's initial guess smoothly loses influence as real data accumulates, never a hard cutover; `scalability`, `automation_potential`, and `long_term_strategic_value` have no measured counterpart today and stay founder-judgment-only, by design, not oversight. `scoring.py` turns blended values into `score_cash_flow`/`score_strategic_value` per goal via min-max normalization *within that goal's own `horizon` bucket* — a short-term cash goal and a long-term asset-building goal are never ranked against each other.
- `src/atlas/brain/strategist.py` — `Strategist`/`SimpleStrategist`, the CEO's capital-allocation function: ranks active goals within their horizon bucket by the appropriate score and maps rank directly to `Goal.priority` (rank 1 = priority 1 = highest); pauses a goal only when it is bottom-ranked in its cohort *and* its own measured revenue shows no improvement over its last 3 readings (the same evidence-gating discipline `propose_improvements` uses for redesign candidates). Not a Registry asset — no manifest, no entrypoint, no capability protocol — a brain-internal component invoked from `CEOBrain.review()`, the same way `Planner`/`Prioritizer` are invoked from `tick()`. Returns decisions only; never mutates a `Goal` or touches `Registry`/`RiskPolicy` — `CEOBrain` applies and logs them itself.
- `src/atlas/brain/improvement.py` — `propose_improvements()`: the continuous-self-improvement principle, structurally enforced, not just documented. Only called from `review()` (never `tick()` — this alone limits churn), only emits a `redesign_*` candidate when it has evidence (a KPI flat/declined over its last 3 readings, or a task category's success rate below 50% over >=3 samples), and skips any target area with an open or recently-resolved (30-day cooldown) redesign task.
- `src/atlas/brain/ceo.py` — `CEOBrain`: `tick()` (plan → prioritize → risk-gate → delegate → monitor, then `absorb_opportunities()`, `_decide_and_apply()` — calls `decision_engine.decide_all()` fresh every cycle, persists+acts only on a materially-changed verdict via `decision_apply.apply_decision()` — and every pipeline-advance bridge above, in sequence — the frequent operational loop) and `review(period)` (evaluates previously `applied` proposals against their `baseline_metrics` → `confirmed`/`needs_review`; reallocates goal priority/status via the `Strategist` — auto-applied and logged, never risk-gated, since re-weighting an existing goal is not a structural change; generates improvement candidates; returns the executive report). `approve(task_id)`/`reject(task_id)` resolve either a plain risk-gated task or one with a linked `Proposal` through the same call; `approve()` also re-dispatches the task (so a founder's "yes" can drive e.g. Content Factory's next stage) and calls `record_revenue()` on the result, same as `tick()`.
- `src/atlas/brain/reporter.py` — `Reporter.summarize(period, memory, kpis)`: plain-dict report (active goals, tasks by status, pending approvals, blocked opportunities, open proposals, KPI deltas, reallocations, `cash_flow` via `cashflow.goal_cash_flow()`) for `daily`/`weekly`/`monthly` windows.
- `src/atlas/brain/console.py` — read-only aggregation over everything the brain already tracks, no new state: `build_console_view()` (goals/pending-approvals/blocked/every registered asset's `report()`/KPIs/`cash_flow` — iterates whatever is currently registered, so a future asset shows up automatically), `find_warnings()` (MAYA stopped / Revenue idle / pending redesign proposals / stale KPIs), `find_stale_kpis()`, `recent_activity()` (tail of the existing decision/outcome log), `build_briefing()` (narrative read of the same state), `get_queue()`/`get_opportunities()`/`get_campaigns()`/`get_system_health()`, `format_console_view()`. Shared by `atlas console`, the REPL's `status` command, and the full-screen app's dashboard — one implementation, not three.

`tests/fixtures/assets/` holds sample manifests used to test `atlas.core` and `atlas.brain` in isolation from the real `assets/` dir: `agent_sample` (`Runnable`), `business_sample` (metadata-only, no entrypoint), `triggerable_sample` (`Triggerable` + `Reportable`, for delegation/monitoring tests).

## Architecture: atlas.assets (operational agents)

Registered, real, tested assets today (see each `manifest.toml` for the authoritative `id`/`kind`/`categories`):

- **`maya`** — Asset #1. `MayaAgent.run()` currently only acknowledges delegated work; real content-generation capability is a stub. This is the single blocker for the whole Asset Engine (see `docs/ATLAS_BUSINESS_BLUEPRINT.md` §6) — nothing else in the Asset Engine can happen for real until this is built.
- **`research`** — discovers opportunities (schema: `{"description", "suggested_category", "source", "source_id"}`), consumed by `atlas.brain.intake.absorb_opportunities`. Produces no revenue signal itself, by design.
- **`revenue`** (`src/atlas/assets/revenue/agent.py`) — `RevenueAgent` routes a task by `category` to one of three placeholder channels under `revenue/channels/`: `AffiliateChannel` (`revenue_affiliate`), `DigitalProductChannel` (`revenue_digital_product`), `ContentAssetChannel` (`revenue_content_assets`). Each `execute()` currently always returns `revenue_generated: 0.0` — a real placeholder (honestly zero), not fabricated data — pending a real integration. **No channel exposes a cost signal today** — this is the standing, still-open gap `docs/ATLAS_BUSINESS_BLUEPRINT.md` §9 flags ("Investment (cost) — Live for Recruitment only"). Recruitment/workforce leads are explicitly *not* a channel here (see `recruitment_workforce` below) — that grew into its own standalone agent once its mission expanded past a single `execute()` call.
- **`recruitment_workforce`** — the only engine producing real, non-placeholder revenue/cost today. Full opportunity pipeline (`discovered → qualified → matched → proposal_ready → active → won/lost`), founder-approval gates (`approve_outreach`, `approve_commitment`), real bill-rate/pay-rate arithmetic. `Opportunity.goal_id`/`task_id` are set once at creation and never rewritten — the precise-attribution rule every later pipeline (affiliate, intelligence, content) copies.
- **`affiliate_department`** (Mission 003, `docs/FIRST_REVENUE_PIPELINE.md`) — `AffiliateDepartmentAgent`, category `affiliate_pipeline`. A reduced, 4-stage slice (`discovered → selected → content_planned`, plus `lost`) of the full 8-stage model `docs/AFFILIATE_OPPORTUNITY_MODEL.md` (Mission 002) designs. First `run()` creates 3 fixed placeholder candidates (no network access); scores them via `score_opportunity()` (`estimated_conversion × commission × (1-competition) × (1-content_difficulty)`, in `scoring.py`); drafts a content brief for the winner. Stops hard at founder approval — **no publishing, no external APIs, ever, in this asset**. A deliberately distinct manifest id from the pre-existing metadata-only `affiliate` (owned by `revenue`) to avoid silently repurposing that org-chart entry; dispatch category `affiliate_pipeline` is likewise distinct from `revenue_affiliate` so the two never collide at the `Delegator`.
- **`affiliate_intelligence`** — `AffiliateIntelligenceAgent`, category `affiliate_intelligence`. A *different* pipeline than `affiliate_department`: ranks candidate affiliate products (`discovered → researched → ranked`) via `DiscoveryAgent`/`ResearchAgent`/`RankingAgent` (`agents.py`), reusing `affiliate_department`'s `AffiliateOpportunity` model, `score_opportunity()`, and — critically — its **same store file** (`.atlas/affiliate_intelligence.json` is separate storage, but this and every asset below it share the *conceptual* opportunity records via `AffiliateStore`/`DEFAULT_STORE_PATH` imported from `affiliate_intelligence.agent`). Every opportunity reaches `ranked`; nothing is auto-selected. The founder chooses which to pursue via one approve/reject task per ranked opportunity.
- **`content_factory`** — `ContentFactoryAgent`, categories `content_factory` / `content_factory_editorial_fix`. Deterministic, template-based generation (`generator.py` — no LLM, no external API) of a full marketing content package (angles, hooks, headlines, CTAs, platform suggestions, video/image/carousel ideas) for an opportunity the founder already chose. Handles three distinct triggers: first generation, an Editorial Review fix request (regenerates only the failed sections), and a founder "request changes" rejection (regenerates fully, up to `REJECTION_LIMIT = 2` before permanently abandoning the opportunity). Planning only — never invokes MAYA's real (stubbed) capability, never publishes.
- **`editorial_review`** — `EditorialReviewAgent`, category `editorial_review`. Automatically evaluates every Content Factory package before the founder ever sees it, via 7 deterministic, rule-based checks (`checks.py`: quality, originality, brand consistency, spam risk, compliance/disclosure, marketing clarity, CTA quality — no LLM). `pass` / `revision_required` (≤2 failed checks) / `reject` (3+ failed, `MAX_REVISION_CYCLES = 2` exhausted). Each failed dimension maps to exactly one `content_package` section, so a fix request names precisely what to regenerate.
- **`publishing_gateway`** — `PublishingGatewayAgent`, category `publishing_gateway`. **The single controlled entry point between ATLAS and external platforms** — and still, deliberately, a dead end: builds and independently re-verifies (`builder.py`, re-running Editorial Review's own compliance check rather than trusting the upstream verdict) a `PublishPackage` from a founder-approved, editorial-passed opportunity, gates queuing behind one more founder approval, and stops at `QUEUED`. No external API is ever called; nothing is ever actually published. `PublishPackage` (`models.py`) is a distinct entity/state machine from `AffiliateOpportunity` — queue status is not conflated with content-approval status.

**The full affiliate chain** (`affiliate_department`/`affiliate_intelligence` → `content_factory` → `editorial_review` → `publishing_gateway`) is real, tested, and fully wired into `CEOBrain.tick()`, but produces zero real external revenue by design — every terminal state is either a founder-approval stop or `QUEUED` with no publish integration. See `docs/ATLAS_BUSINESS_BLUEPRINT.md` for the business-level Cash Engine / Asset Engine framing this all sits under, and note that document's own "Planned" list for Affiliate predates this chain and needs re-reading against the code, not trusted as-is.

`marketing`/`analytics`/`automation`/`cfo`/`coo` remain registered metadata-only, explicitly on hold per the standing instruction not to build them before there's real activity to justify them.

## Architecture: atlas.integrations (real platform connectivity)

A new, peer, dependency-free layer (2026-08-02) — not part of `atlas.core`/`atlas.brain`'s orchestration, importable by assets the same way stdlib is (`affiliate_department` imports it without breaking the "no atlas.core/atlas.brain imports" rule, since this isn't either of those). Exists specifically because platform integration is a real, separate concern from any one asset's business logic, and needs to be provider-agnostic from the start — never one integration per platform bolted onto whichever asset happens to need it first.

- `src/atlas/integrations/base.py` — two genuinely different Protocols, kept separate rather than one "PlatformProvider" interface (the same discipline `atlas.core.capabilities` already uses): `CommerceProvider` (`category`, `validate_link()`, `fetch_recent_sales()` — Digistore24, and future Amazon/AliExpress/Etsy/Shopify/Gumroad) for platforms with trackable links and sales data, and `ContentPublisher` (`publish()`) for platforms that publish content (YouTube/TikTok/Instagram) — defined, **zero implementations anywhere**, since `publishing_gateway` is still deliberately a dead end and building a real publisher is a separate, much bigger decision this layer's existence doesn't imply is ready. `CommerceProvider.category` is a structural fact (Digistore24 *is* an affiliate network) declared by the provider itself — requires no credential or network call, and is what lets `provider_ranking.rank_providers()` find every provider eligible for a category.
- `src/atlas/integrations/digistore24.py` — `Digistore24Provider` (`category = "affiliate"`), the first real `CommerceProvider`. `validate_link()` is fully real, live-verified against the actual production KetoDNA link, and is now the single source of truth for what a real Digistore24 link looks like (moved from `affiliate_department.models.validate_provider_link()`, which delegates here instead of duplicating the regex/parsing logic). `fetch_recent_sales()` is deliberately unimplemented — returns `None` with no `DIGISTORE24_API_KEY` configured, raises a clear `NotImplementedError` if one is set (Digistore24's exact current API surface hasn't been verified against real documentation/a real account, and shipping an unverified guess at code touching real financial data would be worse than leaving it honestly unbuilt). Real revenue recording today still goes through `atlas affiliate revenue record` (founder-reported, unchanged). The credential boundary is deliberate and general: **ranking/ selecting a provider never needs one; only operating a chosen provider for real ever does.**
- `src/atlas/integrations/registry.py` — `PROVIDERS`/`get_provider(name)`, the actual provider-agnostic mechanism: adding a platform means one new class satisfying `CommerceProvider` plus one registry entry, never touching an existing provider or any caller. `affiliate_department.models.SUPPORTED_PROVIDERS` was removed (2026-08-02) — it was a second, hand-maintained allowlist that had already drifted out of being derived from this registry; `get_provider()`'s own fail-closed check is the only place that question is answered now.
- `src/atlas/brain/provider_ranking.py` — `provider_confidence()`/`rank_providers()`: the mechanism that lets the Decision Engine choose *which platform* within an already-worth-pursuing category, not just whether the category is worth pursuing. Mirrors `confidence_score()`'s exact fail-closed shape one level deeper, built from `confidence.py`'s `source_corroboration_score()`/`recency_score()` generalized with an optional `provider` filter (default `None` preserves category-level behavior exactly) rather than duplicated at a new scope. Deliberately a narrower model than category-level confidence — `historical_success`/`measured_outcomes`/`internal_experiments` are absent entirely, since ATLAS doesn't yet attribute real revenue/cost per-provider, only per-goal. `decide()`'s `Decision.chosen_provider`/`context["provider_ranking"]` are populated from this on every `invest` verdict.

## Architecture: operator interface (console / REPL / full-screen app)

Added late in the 2026-07-22 session, with no preceding design doc (the first code in this project to ship that way) — all read-only/dispatch-only, no new business logic:

- `src/atlas/repl.py` — `run_repl()`: a persistent line-based console. Every command (`status`, `briefing`, `departments`, `approvals`, `approve <id>`, `reject <id>`, `queue`, `campaigns`, `opportunities`, `kpi`, `warnings`, `activity`, `exit`) calls straight into `atlas.brain.console`'s data functions or `CEOBrain.approve()`/`reject()` — `dispatch()` is presentation and routing only.
- `src/atlas/app.py` — `run_app()`: a full-screen frame around the same `dispatch()`, redrawing a dashboard (`_render()`) after every command. Adds `_ALIASES`, a natural-language phrasing layer mapped onto the exact same commands (e.g. "how are we doing" → `status`) — anything unrecognized falls through to `dispatch()` unchanged, so no command is lost. **This is what `atlas` with no arguments launches.**
- `src/atlas/speech.py` — optional, best-effort local TTS/STT via Windows' built-in `System.Speech` through PowerShell (no external API, no new dependency). `speak()`/`listen()` never raise — any failure (no mic, no recognizer, PowerShell unavailable) degrades silently to "no speech". Text is passed over stdin/captured from stdout, never interpolated into the PowerShell command string, so briefing/command content can never break out of the shell invocation.
- `src/atlas/cli.py` — `atlas console` (one-shot `format_console_view`), and `atlas` with no subcommand at all routes to `run_app()`.

## Explicitly deferred

Named, not silently dropped: real strategic reasoning (an LLM-backed `Planner`/analyst — the protocol accepts it; wiring an actual model call is a separate cost/API-key decision), actually writing new asset/agent files or rewriting workflows on approval (approving marks a `Proposal` `applied`/`approved_pending_manual_creation`; the mechanical change is a separate explicit step), a scheduler/daemon for 24/7 operation (`tick()`/`review()` are designed to be called on any cadence — cron, Task Scheduler, a Claude Code scheduled routine — standing that up is a deployment step), external report delivery (email/Slack), a live web dashboard/HTTP API (the terminal console/app above is not this), a cross-asset event bus, any real external platform integration anywhere (affiliate network APIs, publishing APIs, payment/conversion tracking), and Mission 004 (`docs/FOUNDER_ASSISTED_BUSINESS.md` — a platform-registration workflow + a `founder_explanation` field on `Task`), which was explicitly designed as "design only, no code changes this mission" and was never subsequently implemented — confirmed absent from `src/` as of this rewrite.
